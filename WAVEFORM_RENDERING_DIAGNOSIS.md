# Waveform Rendering Issues - Diagnosis

**User's Screenshot Analysis:**
1. ✅ Calibration pulse: 2×1 squares (CORRECT!)
2. ❌ Waveform only uses ~1/30th of screen width
3. ❌ ECG looks compressed/weird (not normal PQRST)

---

## Root Cause

### The Math:

**User's canvas:** 1396 × 572 pixels at ~121 DPI

**Medical-correct scale:**
- `pixelsPerSample = mmToPixels(25) / 500 = 119 / 500 = 0.238 pixels/sample`

**Samples needed to fill canvas:**
- `samplesVisible = 1396 / 0.238 = 5866 samples`
- **That's 11.7 seconds of data at 500 Hz**

**Actual data in buffer:**
- Only **200 samples** (calibration pulse: 100 spacer + 100 pulse)
- **That's only 0.4 seconds of data!**

**Result:**
- 200 samples × 0.238 px/sample = **47.6 pixels used**
- 47.6 / 1396 = **3.4% of screen width** ❌
- Remaining 1348 pixels (96.6%) = **EMPTY** ❌

---

## Why Only 200 Samples?

### Two Possible Causes:

1. **No real data from ESP32 watch** ❌
   - Watch not sending waveform data over MQTT
   - Backend not forwarding via WebSocket
   - Only calibration pulse exists (generated by frontend)

2. **Data is arriving but not being stored** ❌
   - WebSocket receiving data
   - But buffer not being updated
   - Need to check useECGViewer hook

---

## The "Compressed ECG" Issue

What user sees as "compressed ECG waveform" is actually:

- 100 samples of calibration pulse data
- All values = `8388608 + 100000` (1mV flat line)
- Rendered at 0.238 px/sample
- **Total width: 23.8 pixels** (exactly 1 big square!)
- Looks weird because it's TINY and followed by 100 samples of baseline

**This is NOT real ECG data** - it's just the calibration pulse!

---

## Why Right Side of Screen is Empty

The code works correctly:

```typescript
const samplesVisible = Math.floor(width / pixelsPerSample); // 5866 samples
const samplesToRender = data.slice(-samplesVisible); // Takes last 5866, but only 200 exist
```

**Result:**
- Takes last 200 samples (all that exists)
- Renders them at correct medical scale (0.238 px/sample)
- Uses only 47.6 pixels
- Remaining 1348 pixels = empty (no more data to render)

**This is actually CORRECT behavior!** If there's only 0.4s of data, it should only use 0.4s worth of screen width at 25mm/s speed.

### Option 1: Fill Screen with Available Data (Stretch) ⚠️

**NOT RECOMMENDED** - This destroys medical scale!

```typescript
// BAD: Stretches to fill screen

```

This is what the OLD code did, which caused the 17× error.

### Option 4: Fix Data Flow (REAL SOLUTION) ✅

**The actual fix:**

1. Check if patient has assigned device
2. Check if device is online and streaming
3. Check if backend is receiving MQTT waveform data
4. Check if backend is broadcasting via WebSocket
5. Check if frontend WebSocket is connected and receiving
6. Check if useECGViewer is appending data to buffer

**This is the ROOT CAUSE we need to fix!**

---

## Diagnostic Questions

1. **Is a watch assigned to this patient?**
   - Check: `patient.assignedDeviceId`
   - If null → No device assigned

2. **Is the watch online?**
   - Check: Device status in backend
   - Check: ESP32 MQTT connection logs

3. **Is watch sending waveform data?**
   - Check: ESP32 logs for MQTT publish
   - Check: Backend MQTT subscription logs

4. **Is backend forwarding via WebSocket?**
   - Check: Backend WebSocket broadcast logs
   - Check: Network tab in browser DevTools

5. **Is frontend receiving WebSocket messages?**
   - Check: Browser console logs
   - Look for `[useECGViewer] 📊 Waveform data received`

6. **Is data being added to buffer?**
   - Check: Buffer length in console
   - Should increase over time if data arriving
