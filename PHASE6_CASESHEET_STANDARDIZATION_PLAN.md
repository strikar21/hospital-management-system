## Executive Summary

Phase 6 will standardize the CaseSheet component and service layer to align with the established patterns from Phases 1-5 (Medications, Investigations, Therapies, Notes).

**Key Challenge:** CaseSheet is fundamentally different from other medical records - it's an **audit trail/timeline** of all medical actions, not a prescribable medical record.

---

## Current Architecture Analysis

### ✅ What Exists:

**1. PatientCaseService** (`services/patient/PatientCaseService.ts`)
- Extends: `BaseService` (NOT `BaseMedicalRecordService`)
- Methods:
  - `getCaseEntries(patientId)` - Fetches timeline with staff resolution
  - `addCaseEntry(patientId, entryData, userId)` - Manual entry creation
  - `acknowledgeAlert(patientId, alertId, userId)` - ⚠️ MISPLACED (should be AlertService)

**2. usePatientCaseSheet** (`hooks/usePatientCaseSheet.ts`)
- **Different pattern** - Not for CRUD operations
- Purpose: Pagination, filtering, sorting, UI utilities
- Methods:
  - Pagination: nextPage(), prevPage(), goToPage()
  - Touch handlers: swipe navigation
  - Formatters: getEntryTypeLabel(), formatEntryDescription()
- **Does NOT** handle add/update/delete operations

**3. CaseSheetBook** (`CaseSheetBook.tsx`)
- Display-only component
- Uses usePatientCaseSheet for pagination
- Read-only timeline view
- No CRUD operations

---

## Key Differences: CaseSheet vs Other Medical Records

| Feature | Medications/Therapies/Notes | CaseSheet |
|---------|----------------------------|-----------|
| **Type** | Prescribable medical record | Audit trail / Timeline |
| **Creation** | User prescribes/adds | Auto-generated by atomic operations |
| **CRUD** | Full CRUD operations | Mostly read-only |
| **Purpose** | Medical treatment | Historical record |
| **User Action** | "Prescribe medication" | "View case timeline" |

## Senior Tech Lead Checklist - Analysis

### 1. Do I have a detailed failproof plan?

**Question:** Should CaseSheet follow the same pattern as Medications/Therapies/Notes?

**Analysis:**
- ❓ CaseSheet is NOT a medical record type - it's the audit trail OF medical records
- ❓ Users don't "prescribe case entries" - they're auto-generated
- ✅ PatientCaseService.addCaseEntry() EXISTS but is rarely used directly
- ✅ Some manual case entries are added (notes, status changes)
- ⚠️ acknowledgeAlert() is misplaced in CaseService

**Recommendation:**
- **Option A:** Refactor CaseSheetService to extend BaseMedicalRecordService for consistency
- **Option B:** Keep CaseSheetService as-is since it's fundamentally different
- **Option C (BEST):** Partial refactoring - standardize what makes sense, keep unique features

### 4. Have I thought about the fixes with logic and sense?

**Logical Analysis:**

**What Makes Sense:**
1. ✅ Standardize CaseSheetService to extend BaseMedicalRecordService
   - Provides consistent API (getRecords, addRecord, etc.)
   - Enables future enhancements (filtering by status, timeline queries)

2. ✅ Keep usePatientCaseSheet as-is
   - Timeline pagination is unique to case sheet
   - Swipe navigation, formatters are UI-specific
   - Not a typical CRUD hook - it's a timeline/pagination hook

3. ✅ Keep CaseSheetBook as display component
   - No CRUD operations needed in UI
   - Read-only timeline view is correct design

4. ✅ Move acknowledgeAlert() to AlertService
   - Alerts should have their own service
   - Cleaner separation of concerns

**What Doesn't Make Sense:**
1. ❌ Creating useCaseSheet CRUD hook (like useMedications)
   - Case entries are auto-generated, not user-created
   - Would add complexity without benefit

2. ❌ Creating CaseSheetContainer with add/edit buttons
   - Users don't manually add case entries
   - Timeline is read-only by design

### 5. Have I thought this out like a senior tech lead?

**Senior Tech Lead Assessment:**

**Root Cause:** CaseSheet service layer is inconsistent with other services, but the component layer is actually well-designed for its purpose.

**Proper Fix:**
1. Standardize the service layer (CaseSheetService extends BaseMedicalRecordService)
2. Keep the unique hook (usePatientCaseSheet for pagination/timeline)
3. Keep the display component (CaseSheetBook is correct design)
4. Extract alert operations to separate AlertService

**NOT a Quick Fix:** This is a targeted architectural improvement, not a workaround.

## Recommended Implementation Plan (Option C)

### Step 1: Create CaseSheetService
**Location:** `hospital-display-app/src/services/CaseSheetService.ts`

**Changes:**

```typescript
export class CaseSheetService extends BaseMedicalRecordService<caseSheetEntry> {
  protected getConfig(): MedicalRecordConfig {
    return {
      recordType: 'case-entries',
      recordTypeSingular: 'case entry',
      recordTypePlural: 'caseEntries'
    };
  }

  // Inherited from BaseMedicalRecordService:
  // - getPatientRecords() → getCaseEntries()
  // - addRecord() → addCaseEntry()

  // Case-specific overrides:
  protected transformAddPayload(entryData: any, userId: string): any {
    return {
      entryType: entryData.entryType,
      description: entryData.description,
      performedBy: entryData.performedBy || userId,
      findings: entryData.findings,
      recommendations: entryData.recommendations,
      followUpDate: entryData.followUpDate,
      severity: entryData.severity,
      category: entryData.category
    };
  }

  // Static wrappers for backward compatibility
  static async getCaseEntries(patientId: string): Promise<caseSheetEntry[]>
  static async addCaseEntry(patientId: string, entryData: any, userId: string): Promise<any>
}
```
