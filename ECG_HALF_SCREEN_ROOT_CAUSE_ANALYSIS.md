### 3. Mathematical Analysis

#### User's Screen (from previous conversation):

#### Calculate Expected Values:
1. **pixelsPerSecond** = (121 DPI / 25.4 mm/inch) × 25 mm/s = **119 pixels/second**
2. **pixelsPerSample** = 119 / 500Hz = **0.238 pixels/sample**
3. **samplesVisible** = 1396 / 0.238 = **5865 samples** (fits on screen at 25mm/s speed)

#### Timeline of Data Growth:
- **T = 0s:** Calibration pulse loads = 200 samples
- **T = 0.4s:** 200 + 200 = 400 samples

### 4. ROOT CAUSE IDENTIFIED ✅

**The Issue:** samplesVisible (5865) > maxSamples (4000)

**What This Means:**
- The waveform will NEVER enter Phase 2 (circular buffer mode)
- It will ALWAYS stay in Phase 1 (growing mode)
- Phase 1 renders from right edge: `startX = width - (data.length × pixelsPerSample)`

**At Maximum Buffer (4000 samples):**
- startX = 1396 - (4000 × 0.238)
- startX = 1396 - 952
- startX = **444 pixels from left edge**

**Result:** Waveform only uses **952 pixels** out of **1396 pixels** = **68% of screen width**

This matches user's observation: **"only fills half the screen"** (actually ~2/3)

### 5. Why It Doesn't Fill the Screen

The waveform never transitions to Phase 2 because:
```
maxSamples (4000) < samplesVisible (5865)
```

So it stays in Phase 1 forever, rendering from the right but never filling the left side.

## THREE PROBLEMS IDENTIFIED

### Problem 1: Buffer Size vs Screen Capacity Mismatch ❌
- Buffer: 4000 samples (8 seconds)
- Screen capacity: 5865 samples (11.7 seconds)
- **Result:** Never fills screen, stuck in Phase 1

### Problem 2: Comment vs Code Discrepancy ❌
- Line 75 comment: "Buffer stores 1000 samples"
- Line 78 code: `visibleSeconds = 8` → 4000 samples
- **Result:** Confusion about actual buffer size

### Problem 3: Frontend Calibration ❌
- Calibration generated by frontend software
- Medical standard: hardware generates calibration
- **Result:** Cannot validate entire signal chain (sensors→ADC→transmission→display)

## SOLUTION OPTIONS

### Option A: Increase Buffer Size to Match Screen ✅ RECOMMENDED
```typescript
const visibleSeconds = 12;  // Increase from 8 to 12 seconds
const maxSamples = samplesPerSecond * visibleSeconds; // 6000 samples
```

**Why This Works:**
- maxSamples (6000) > samplesVisible (5865)
- Waveform will transition to Phase 2 (circular sweep mode)
- Full screen will be used
- Matches ICU monitor behavior

**Pros:**
- Minimal code change
- Keeps medical 25mm/s speed standard
- Enables proper circular buffer sweep

**Cons:**
- Slightly more memory (6000 vs 4000 samples per lead)
- 6000 samples × 8 leads × 4 bytes = ~192KB (negligible)

### Option B: Simplify to Full-Screen Adaptive Rendering
```typescript
// Remove medical speed calculation, just fill screen
const pixelsPerSample = width / Math.min(data.length, maxSamples);
```

**Pros:**
- Always fills screen
- Simpler code
- No DPI detection needed

**Cons:**
- Loses medical 25mm/s standard speed
- Waveform speed changes as buffer fills
- Not medically accurate

### Option C: Hybrid (Adaptive Phase 1, Fixed Phase 2)
```typescript
if (data.length <= maxSamples / 2) {
  // Phase 1: Adaptive - fill screen during startup
  const pixelsPerSample = width / data.length;
} else {
  // Phase 2: Fixed 25mm/s medical speed
  const pixelsPerSample = mmToPixels(25) / 500;
}
```

**Pros:**
- Fast startup (fills screen immediately)
- Medical accuracy once running

**Cons:**
- More complex logic
- Speed transition might be jarring
